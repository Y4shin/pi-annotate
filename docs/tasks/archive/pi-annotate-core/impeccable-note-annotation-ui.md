### Impeccable Handoff: annotation-ui

The implementation created bare-minimum functional UI for this slice.
The following surfaces are ready for design refinement:

#### Surfaces
- `.pi/extensions/pi-annotate/client.ts` (inlined `<style>` block in `htmlShell()`): Full annotation-app stylesheet — document content layout, block/paragraph margin markers, floating range-comment button, comment forms, annotation list, whole-document note box, submit button, and done state. Currently flat, single-column, gray utilitarian styling with no design system, spacing scale, or visual hierarchy beyond raw functional defaults.
- `.pi/extensions/pi-annotate/client.ts` (inlined IIFE in `clientScript()` — `setupAnnotationUI`, `renderAnnotations`, `createCommentForm`): The annotation panel DOM — "Annotations" heading, deletable `<ul>` list with kind-label + comment + `×` delete button, whole-document note textarea + "Add note", and "Send to agent" submit button that yields to a green "Done — you can close this tab" state. No states for empty/hover/active/disabled beyond minimal CSS; no loading or error affordances; success state is a single static line.
- `.pi/extensions/pi-annotate/client.ts` (inlined IIFE — `setupBlockMarkers`): A `💬` margin marker button positioned absolutely at the top-right of each rendered markdown block (`<p>`, `<h1>`, `<pre>`, etc.). Revealed on hover via opacity. Only visual affordance is the emoji glyph and hover-opacity; no tooltip, no "already annotated" indicator, no focus styling.
- `.pi/extensions/pi-annotate/client.ts` (inlined IIFE — `setupRangeSelection`, `addRangeButton`): A floating "Add comment" button that appears when the user selects text in the document content area. Positioned absolutely top-right of `.content`, not near the selection. No visual connection to the highlighted range, no positioning near the caret, no selection highlight styling.

#### Suggested commands
- `/impeccable layout .pi/extensions/pi-annotate/client.ts` — The annotation panel, content area, and margin markers share a single 720px column with absolute-positioned overlays that collide (range button and block markers both pin to the top-right corner). A layout pass should separate the reading column from the annotation affordances, position the range-comment button near the selection rather than the corner, and give the annotation panel a distinct region (sticky sidebar, collapsible drawer, or visually separated footer).
- `/impeccable shape .pi/extensions/pi-annotate/client.ts` — The three annotation input modes (inline range form, block-appended form, whole-document note) have inconsistent shapes and placements. Shape them into a coherent, predictable interaction pattern so the user always knows where the comment field will appear for each kind.
- `/impeccable typeset .pi/extensions/pi-annotate/client.ts` — The annotation list items render kind metadata and comment text in a cramped flex row with `white-space: nowrap` on the meta label. Long quotes truncate at 80 chars with a bare `…`. Typesetting should give each annotation kind a scannable, readable structure (quote, block index, note) with proper wrapping and visual weight.
- `/impeccable colorize .pi/extensions/pi-annotate/client.ts` — All styling uses raw hex grays (`#f4f4f4`, `#ddd`, `#eee`, `#fee`/`#fcc`/`#c00`, `#e8f5e9`) with no theme, no annotation-kind color coding, and no light/dark consideration. A colorize pass should introduce a coherent palette, distinguish the three annotation kinds visually, and give the destructive `×` and success "Done" states appropriate semantic color.
- `/impeccable harden .pi/extensions/pi-annotate/client.ts` — Several interactive states are missing or fragile: no disabled state for the "Send to agent" button while a fetch is in-flight (the client-side `submitted` guard silently no-ops), no retry affordance on submit failure (it logs to console and resets `submitted` with no UI signal), no keyboard/focus styling on markers and delete buttons, no empty-list-onboarding copy beyond "No annotations yet.", and the floating range button reuses the same corner position as block markers causing overlap.

#### Notes
- This is a zero-dependency, jsdom-free client: the annotation UI is an inlined IIFE string returned by `clientScript()` and the CSS lives in a `<style>` block inside `htmlShell()`, both in `client.ts`. There is no separate `.css`, `.tsx`, or component file — a designer edits the inlined template strings directly or should be aware the "file" is a TS string literal.
- The client uses `document.createElement`/`appendChild` for all annotation UI (not innerHTML for the panel), so DOM structure is stable and discoverable; only the rendered markdown body uses `innerHTML`.
- XSS escaping is already in place (`escapeHtml`, `textContent` for user comments) — preserve it; do not switch comment rendering back to `innerHTML`.
- A test-only seam `globalThis.__annotateTest` is exposed on the `globalThis` object; it is harmless in a real browser but the designer should not rely on or remove it.
- The fake-DOM test harness in `test/client.test.ts` implements simple descendant selectors (`querySelector`/`querySelectorAll`) and innerHTML serialization. If class names or selectors change, the tests in `test/client.test.ts` that key off `[data-action="..."]` and class names (`.annotation-item`, `.delete-btn`, `.block-marker`, `.range-marker`, `.comment-form`, `.note-box`, `.submit-btn`, `.done-state`, `.empty`) will need matching updates.
- No real browser was opened during implementation (`PI_ANNOTATE_NO_BROWSER=1`); visual verification of the design should be done by the designer in an actual browser session.
